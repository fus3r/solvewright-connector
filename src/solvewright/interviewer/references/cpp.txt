# C++ live rounds

Follow case-generation.txt for the problem's quality: a real scenario, a small callable interface, a worked example and a design choice, then new requirements that stress that design. The language changes the runtime, not this bar. Do not dictate the internal classes, containers or algorithm. Follow the design-substance gate in case-generation.txt: for standard or stretch, a prescribed CRUD class with a few map assignments is too weak. State the meaningful design freedom in the opening. Use English and no em dashes.

The candidate writes workspace/solution.hpp. Public tests are workspace/tests/test_*.cpp. Private checks are .examiner/checks/test_*.cpp. Both include "solution.hpp" and "check.hpp", use only the shipped TEST(name), CHECK(expression), CHECK_EQ(actual, expected) macros and the C++ standard library. No external frameworks, custom main(), reference includes, network, files, processes, threads or wall-clock timing. TEST names are plain identifiers, not quoted strings. check.hpp supplies main(): run the compiled test with --list to list names, then with one name to run that test. Each test gets a fresh process and a 5 second safety limit in the browser; this is never a performance criterion.

The exact header is context/interviewer/tools/check.hpp, also installed at workspace/.sw/check.hpp. Do not edit it or write a replacement. The page supplies that identical header. Private checks use the same includes even when stored outside workspace; their browser location changes. Keep private checks self-contained, with expected values in the test, and do not include other private files.

Keep .examiner/checks/checks.json in the existing format: {"checks": [{"id": "test_part1.cpp::case_name", "part": 1, "label": "a short plain case name", "note": "one sentence pointing at the case without giving the fix"}]}. Declare every private TEST with its exact file and name. Release only the current part's tests and checks, adding later ones when that part opens.

State these rules in the opening and in README.md: C++20, no exceptions (an operation that would throw aborts), one thread, no wall-clock timing. Explicit throw/try/catch cannot compile with -fno-exceptions. Do not make error behavior depend on exceptions: use return values or documented valid-input constraints. The browser uses Clang 21 and libc++ on wasm32, an 8 MiB stack and 256 MiB memory. Avoid host-specific extensions, inline assembly and reliance on pointer size, unordered iteration order or standard-library allocation counts.

Cost requirements must be measurable by counting, with explicit bounds in the contract: replace global operator new to count allocations, or use instrumented types to count comparisons or copies. Include a discriminating counted check when a part has a cost requirement. Allocation checks must use strings longer than 22 characters: the browser's libc++ keeps fewer characters inline than macOS's. Build inputs before enabling the counter, disable it before assertions, and allow reasonable container overhead instead of depending on one library's capacity policy. A no-throw replacement operator new uses malloc and aborts on failure, never throw std::bad_alloc; provide the matching delete operators. Keep problem sizes small enough to run comfortably within the safety limit.

Before releasing EVERY part, verify inside your agent sandbox. Use the compiler named by session-settings.json under cppCompiler. Its native flags are -std=c++20 -fno-exceptions -O1 -Wall -I. -I.sw, from a disposable .examiner verification folder holding the reference as solution.hpp and the identical .sw/check.hpp. Clang diagnostic flags may also be used: -fno-color-diagnostics -ferror-limit=8. The browser additionally sets WebAssembly linker flags -Wl,-z,stack-size=8388608 -Wl,--max-memory=268435456; those target-specific flags do not apply to a native executable. Compile each test file alone, not all tests into one executable. Run --list, then every listed name in its own invocation. Prove the reference passes all released public tests and private checks, and that a plausible wrong solution fails. Validate the reference on representative legal shapes within the stated bounds, not only tiny examples. For a dependency graph, include shared subgraphs as well as chains: a recursive walk may repeat shared work exponentially even on 60 jobs. This is a correctness and safety-limit check, not wall-clock scoring. Keep cost requirements explicitly counted. Record commands, outcomes and which wrong behavior was rejected in .examiner/manifest.json. Preserve workspace/solution.hpp as the candidate's starter or work, never leave the reference there. If compilation or execution is blocked, report the failure rather than claiming a verified setup or releasing it.
